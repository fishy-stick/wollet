# v1.1.0 开发计划

状态：开发中。更新日期：2026-09-19。

## 版本目标

本版本改善 Windows 客户端的升级体验和远程关机提示，交付两项能力：

- **更新保留配对**：运行新版客户端即可更新已有安装，保留有效的设备凭据并恢复连接。
- **同步关机倒计时**：从管理页面发起关机后，目标电脑同步显示剩余时间，并响应管理页面的取消或立即执行操作。

服务端、管理页面和 Windows 客户端统一以 `v1.1.0` tag 发布。两个需求完成并通过联合验收后发布，发布日期根据验收进度确定。

本文描述目标行为；当前已实现的通信方式见 [通信协议](protocol.md)。

## 客户端更新与配对保留

### 背景

用户反馈，客户端更新时无法顺利替换已有版本，再次打开程序会提示重新输入 Token 配对。更新流程需要识别已有安装，保留有效绑定，并在程序替换完成后恢复后台服务。

现有程序与配置分别保存在 `%ProgramFiles%\Wollet` 和 `%ProgramData%\Wollet\client.json`，设备密钥由 DPAPI 保护。`InstallCoordinator.InstallAsync` 已包含复用同一服务端有效凭据的逻辑，重新配对提示的具体成因仍待排查。当前卸载流程会删除本地凭据，更新流程应直接替换程序并保留配置。

### 交付范围

采用手动下载并运行新版客户端的更新方式，提供明确的更新入口，完成程序替换、凭据复用和后台服务恢复。自动检查版本、自动下载和静默安装不在本版本范围内。

界面展示已安装版本和当前程序版本，根据比较结果提供更新或修复；禁止旧版本覆盖新版本。缺失或无效的版本信息应有明确提示并阻止覆盖。

版本解析采用 `NuGet.Versioning 7.9.0`，按数字版本与预发布标识比较，忽略构建元数据。开发测试使用递增的 `1.1.0-dev.N`，发布前验收使用 `1.1.0-rc.N`，最终发布 `1.1.0`。预发布标识统一小写，同时兼容旧程序的四段数字版本。

### 验收标准

- 已配对设备运行新版客户端后，能够识别并更新已有安装，无需先卸载。
- 更新保留服务端地址、设备身份与有效凭据，无需生成或输入新的 Token。
- 更新完成后服务恢复连接，管理页面仍显示原设备，不产生重复设备记录。
- 网络不可达与凭据失效有不同提示，临时连接失败不会被视为需要重新配对。
- 更新失败时保留配置，并提供可操作的恢复提示。
- 按版本号数值比较新旧版本，构建元数据不影响优先级；验证新版更新、同版修复、降级拦截与未知版本处理。
- 覆盖服务运行中更新、网络不可达、凭据失效及更新失败场景，首次安装流程正常。

### 待确定的设计

- 配置缺失、损坏、凭据撤销或切换服务端时的重新配对边界。

### 实现与验证进度

已实现独立更新入口、版本比较、保留凭据的离线更新，以及先暂存、再停止服务和替换程序的流程。替换或启动失败时尝试恢复旧程序与原服务运行状态，恢复失败则保留可用备份并报告修复提示。

自动化测试覆盖正式版与预发布版排序、无需网络或凭据写入的更新、缺失配置拦截、替换与恢复流程。两种单文件发行形式已完成构建和版本资源检查；真实 Windows 服务从 `v1.0.4` 升级、DPAPI 凭据复用和界面显示仍待安装环境验收。

## 客户端同步关机倒计时

### 背景

当前 10 秒倒计时仅在管理页面中显示，结束后页面才调用关机 API。服务端发送的 WebSocket `shutdown` 消息仅携带 `commandId`，客户端确认收到后执行系统关机，因此目标电脑上的用户无法提前看到倒计时。

本版本需要扩展关机操作的协议与状态，并建立后台服务向 Windows 用户桌面展示提示的机制。

### 交付范围

沿用 10 秒倒计时，在管理页面和目标客户端同步展示同一次关机操作的剩余时间。管理页面保留取消和立即执行功能，客户端同步响应操作结果。客户端提示形式及本地操作权限在实现前确定。

### 验收标准

- 管理页面发起关机倒计时后，目标客户端在倒计时阶段显示提示。
- 两端显示同一次关机操作的剩余时间，到期执行一次关机；客户端不会额外开始第二轮倒计时。
- 管理页面取消或立即执行时，客户端同步更新，不残留过期提示。
- 按确定的方案验证断线、重连、页面关闭、服务重启、重复请求及 Windows 会话变化时的行为。

### 待确定的设计

- 客户端采用弹窗、托盘窗口还是其他提示形式，是否允许本地取消或立即执行。
- 倒计时与最终关机的执行责任，以及网络延迟和时钟偏差的处理方式。
- 断线、重连、页面关闭、服务重启及重复请求时，关机操作的继续或取消规则。
- Windows 锁屏、无登录用户和多用户会话时的提示与执行行为。
- 协议版本、能力协商、消息字段及旧版本兼容机制。

## 兼容与升级

本版本以向后兼容为要求。产品版本 tag 与 WebSocket 的 `protocolVersion` 分别管理，协议版本和能力协商方式由协议设计确定。

| 版本组合 | 预期行为 |
| --- | --- |
| 新服务端与旧客户端 | 保留原有关机能力，不向旧客户端发送无法识别的扩展消息 |
| 旧服务端与新客户端 | 正常连接并保留原有关机能力 |
| 新服务端与新客户端 | 启用同步关机倒计时 |

推荐部署顺序为先升级服务端，再升级客户端。客户端程序更新本身不依赖服务端先行升级；同步倒计时需要两端共同支持。

## 实施与发布

### 开发顺序

1. 排查并修复客户端更新与凭据保留，验证旧版直接升级流程。
2. 确定倒计时交互和异常场景规则，实现协议扩展、桌面提示及兼容处理。
3. 完成联合验收，更新通信协议文档与发布说明。

各项待定设计应在对应功能实现前明确，并补充为可验证的验收条件。

### 联合验收

以 `v1.0.4` 为升级验证基线，验证已配对客户端直接升级到 `v1.1.0` 后保留原设备身份，无需重新输入 Token；连接新版服务端后，可正常使用同步倒计时。

包含 .NET Runtime 和 framework-dependent 两种客户端发行形式均需覆盖完整流程：升级保留配对、恢复连接、同步倒计时、取消关机和执行关机。同时验证兼容矩阵中的三种版本组合。

### 发布要求

- 两项功能的验收标准和联合验收全部通过后，在对应提交上创建并推送 `v1.1.0` tag。
- 发布前核对远端 tag，确认目标版本号可用。
- 现有发布流程由 `v*` tag 触发，构建服务端镜像和两个 Windows 客户端发行文件，并创建 GitHub Release。
- 发布说明应包含更新方式、升级顺序、同步倒计时的启用条件和旧版本兼容行为。
- 已发布 tag 保持不变，后续修复使用新的补丁版本。

## 后续需求

### 休眠选项

状态：待评估，目标版本待定，不纳入 `v1.1.0`。

为远程关机功能增加可选的休眠方式，让用户能够选择使目标电脑进入休眠，而不是关闭系统。

交互设计应保持现有界面的极简体验。选项的入口、呈现方式及默认行为尚未确定，留待后续版本规划时讨论。

后续评估事项：

- 如何在保持简洁的前提下选择关机或休眠。
- 休眠是否沿用倒计时、取消和立即执行的交互。
- 客户端休眠能力检测、不支持休眠时的提示，以及指令与状态的协议扩展。
