# v1.1.0 版本信息与兼容提示规划

状态：待实现，纳入 v1.1.0。

## 交付目标

维护统一的版本与功能目录，根据两端版本及实际能力计算不可用功能。管理页面和客户端管理窗口使用相同的判断规则，默认仅展示短状态标签，具体差异在悬浮详情中查看。

本版检测当前连接的两端及本地安装包，不查询远端最新版本、不自动下载、不强制升级。功能差异不阻止仍可使用的基础操作。

## 版本与功能目录

在仓库中维护一份可供 Go、C# 和页面共用的结构化目录，作为功能名称、依赖条件和版本映射的唯一来源。两端构建时读取或生成各自使用的数据，避免分别维护文案和版本判断。

目录包含两部分：

| 数据 | 内容 |
| --- | --- |
| 功能定义 | 稳定功能 ID、用户可读名称、简短说明、所属端，以及需要的服务端／客户端能力 |
| 版本清单 | 组件类型、产品版本或已验证版本区间、该版本具备的功能与协议能力 |

功能 ID 与协议能力 ID 分开：一个用户功能可以依赖多个能力，一个协议能力也可以支撑多个用户功能。例如“客户端倒计时”“客户端取消关机”均依赖两端的 `shutdown-plan.v1`；“更新保留配对”是客户端自身功能，不因服务端较旧被标记为不可用。

不必为每个补丁版本复制整份清单：功能相同的已验证版本可共用区间，版本条目也可继承并明确新增或移除功能。发布检查必须核对清单与实现，不能默认功能永远只增不减。

初始目录覆盖现有基础功能和 v1.1.0 新功能，历史版本只登记已经核实的支持情况。开发版、候选版按实际构建登记，不能因为版本以 `1.1.0` 开头就推断所有规划功能均已完成。尚未发布的功能可以列为规划，但不参与当前兼容结论。

## 差异计算

1. 获取后台服务实际运行版本、服务端版本、各自声明的能力和当前协商结果。
2. 根据版本目录得到已知版本的预期功能集合；对未知版本保留未知状态，不套用最近的已知版本。
3. 按每项功能的依赖条件计算当前可用集合。跨端功能必须满足两端依赖，单端功能仅检查对应端。
4. 在本次连接涉及、且已知某端提供的功能范围内，找出因另一端缺少依赖而不可用的功能，汇总需要更新的组件。双方都没有的未来功能不列为当前缺失。
5. 结合版本是否可比较、目录中是否有明确的升级目标，生成短标签和详情列表。页面与客户端渲染结构化结果，不包含按具体功能编写的分支。

实际声明和协商结果优先于版本目录。版本清单用于说明和已验证的旧协议回退，不能覆盖实际协商结果、强行启用功能。版本与能力不符时显示“兼容性受限”，不能直接断言升级一定可解决。缺少能力字段只有在握手成功、已确认采用旧协议时才可按已知旧协议解释；超时或接口失败不是缺少能力的证据。

现有 `ready.capabilities` 表示本次协商结果，不能当作服务端支持的全部能力。实现时须分别提供两端支持能力与本次协商能力，才能准确判断缺少能力的一方。

## 轻量提示规则

两端采用统一的状态模型。正常状态不额外增加徽标；异常状态在版本信息旁最多显示一个短标签。功能差异比单纯版本差异优先，网络及同步状态由原有状态区域承担。

| 条件 | 默认标签 | 悬浮详情 |
| --- | --- | --- |
| 功能缺失，确定由较旧组件造成，且目录中有支持该功能的更新版本 | 客户端可升级／服务端可升级 | 两端版本、当前不可用功能，以及需更新哪一端 |
| 两端版本不同，但当前所需功能均可用 | 版本不一致 | 两端版本；“当前功能均可用，无需为保持一致而升级。” |
| 存在确定的功能缺失，但版本未知、映射不完整或能力与版本不符 | 兼容性受限 | 已确认不可用的功能及缺少能力的一端；不猜测最低版本 |
| 无法取得有效版本，且功能支持也无法判断 | 版本未知 | 缺失的信息及“连接后可重新确认” |
| 版本一致、功能支持正常 | 不增加标签 | 常规版本信息仍可查看 |

“可升级”表示已知目录中有合适版本，不表示已联网查到最新发行版或已经下载安装包。开发构建仅提供开发构建说明，不引导用户把正式发布页中可能较旧的文件当作可用更新。

版本比较沿用已有版本语义：忽略构建元数据，正确处理预发布标识；无法解析时显示未知。仅构建元数据不同不产生“版本不一致”标签。两端无需强制使用相同产品版本。

悬浮详情示例：

> 客户端：1.0.4 · 服务端：1.1.0
>
> 当前不可用：
>
> - 客户端关机倒计时
> - 客户端取消与立即关机
>
> 更新客户端可启用以上功能，基础远程关机仍可使用。

示例文案由目录与差异结果生成，不作为针对关机功能的专用模板。关联且描述重复的功能可以在目录中分组，详情按组展示；不列协议字段名或内部能力 ID。

悬浮详情必须支持键盘聚焦，手机上点击标签也能打开；点击外部或按 Escape 关闭。鼠标移入详情区域时保持可见，长内容可换行。需要可点击的“更新说明”时使用可交互浮层，不仅依赖原生 `title`。

## 管理页面

- 在当前设备的状态信息附近显示客户端版本，标签紧邻版本。设备切换时一并更新，不在设备列表上堆叠提示。
- 服务端版本在页面底部低强调展示；详情中可以同时列出两端版本。
- 默认不展开功能清单，不增加常驻横幅、额外确认框或单独的更新大按钮。
- 浮层中的“更新说明”按需说明应更新客户端还是服务端。客户端更新说明沿用手动下载、运行新版并保留配对的流程，无需卸载。
- 离线时，已知信息标注“上次连接”，不根据空的在线能力集合重新计算升级提醒。重连后以新连接结果刷新。
- 已协商功能但业务状态尚未同步时，显示原有“正在同步”状态，不把暂时不可操作列为版本缺失功能。

页面不会因两个版本不同而改变关机方式；实际操作继续由能力协商选择相应协议。

## Windows 客户端管理窗口

- 保留顶部“已安装版本／当前程序版本”与更新、修复入口；在服务端版本旁增加同样的短标签和悬浮详情。
- 兼容信息与服务运行状态、网络错误、安装进度分别展示，不互相覆盖。
- 以后台服务实际运行版本判断连接兼容性，不能把当前打开的新版安装包视为已经完成升级。
- 打开窗口、安装或更新完成后检查；提供低强调的“刷新状态”入口。优先从本地后台服务读取状态，不创建第二条设备 WebSocket 连接。
- Windows 浮层同样支持鼠标悬浮、键盘聚焦与点击展开。日常桌面提示进程、关机弹窗和托盘不增加升级通知。

旧服务端的网页无法获得本次界面改动；新版客户端管理窗口使用随自身发布的目录和实际连接信息说明兼容情况。

## 实现顺序

1. 建立统一的功能目录与版本清单，定义继承、版本区间及目录校验规则。
2. 增加构建版本来源与可选握手字段 `clientVersion`、`serverVersion`；Go 发布版本由 tag 注入，本地未知构建不冒充正式版本。
3. 在已有认证的 REST/SSE 和本地只读 IPC 中补齐运行版本、两端支持能力、协商结果及检测状态。旧端缺失字段保持兼容。
4. 实现独立的差异计算，输出标签类型、受影响组件、不可用功能列表、原因与可选升级目标。两端用同一套样例校验结果，未知功能 ID 不影响连接。
5. 接入页面与客户端的短标签和浮层，目录中的名称与说明按普通文本呈现；更新链接仅使用项目维护的可信入口。
6. 完成版本组合、缺失字段及多种交互方式的验收。以后增加功能主要修改目录及相应能力实现，不修改提示组件的判断分支。

本版先使用随程序发布的目录，不引入在线目录更新服务。目录较旧时不能推断未来版本的全部功能；仅展示能够确认的差异和版本信息。

## 验收标准

- 新旧两端组合正确识别受影响组件，基础远程关机仍可正常使用。
- 增加一项测试功能定义即可产生新的差异条目，无需修改页面或客户端提示组件。
- 单端功能不因另一端版本不同而误报；双方均无的未来功能不显示为当前缺失。
- 版本不同但功能一致时只显示中性“版本不一致”；只差构建元数据时不提示版本不一致。
- 版本未知、未登记的预发布版、能力与版本冲突、断网和同步中有各自正确的结果，不将未知当作缺失。
- 新连接重新计算当前版本和能力，离线缓存明确标注历史，不残留“已升级”的结论。
- 功能清单仅在悬浮、聚焦或点击后展开，移动端、键盘及高 DPI 下均可读取。
- 不阻止现有功能，不增加远端发布源查询、自动下载、日常桌面通知或额外设备连接。
